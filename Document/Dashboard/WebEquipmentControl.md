# 웹 장비 고장 제어와 영향 관측

장비 **오류·복구**에서 고장 유형을 선택한다. 자동화 카메라 재부팅은 기본 60초+재확인 2초, 필수 센서 현장 수리는 기본 900초+재확인 2초 후 재개한다. 편집 가능한 가정값이며 에디터 `Failures → Repair`에서 바꾼다. 갠트리 고장은 수동 수리가 필요하다. 남은 시뮬레이션 시간과 대피/복귀 상태를 웹에 표시한다.

오버뷰 하단의 **중앙도로 실제 주행**은 야드 01~09와 10~23 사이 16m 도로의 실제 적재/빈차 이동 거리다. 예정 경로 수와 구분한다. 중앙도로는 기존 남/중/북 도로 그래프의 일부이며 차로 중심은 Y=-155.5m(야드 방향), -164.5m(복귀 방향)로 노면 폭 안에 배치한다. 기존 경로 비용·도로 예약·LiDAR가 통행을 결정한다. 9m 차로 간격 안에서 최소 회전반경을 위반하는 연속 두 회전(유턴)은 경로 탐색에서 제외하고 공간이 있는 연결로를 사용한다.

터미널 오버뷰에서 STS·RMG·AGV를 클릭하고 **오류·복구** 탭을 연다. **오류 발생**은 STS/RMG의 필수 센서 고장 또는 AGV 주행 고장을 엔진에 입력한다. **수리·복구**로 해당 고장만 해제한다. 접수와 실제 엔진 적용 완료를 구분하며, 엔진이 꺼져 있거나 오래된 실행 기록을 보는 동안에는 제어하지 못한다. 기존 엔진은 새 DLL을 빌드한 뒤 다시 실행해야 한다.

STS/RMG 작업 재배정은 `EquipmentFailureRecovery.md`의 도달 범위·레일 간격·적재 조건을 따른다. 이미 잠기거나 매달린 화물은 수리 대기한다. AGV는 현재 위치·화물·도로 예약을 유지하고 신규 배차에서 제외된다. 다른 차량은 기존 도로 그래프·예약·LiDAR에 따라 대기하거나 우회하며, 고장 차량을 강제로 움직이거나 화물을 순간 이동시키지 않는다. 좁은 길을 고장 차량이 막으면 통행이 계속 보장되는 것은 아니다.

오버뷰는 엔진의 실제 갠트리 위치, 스프레더 위치, AGV 위치를 1초 간격으로 갱신한다. 빨간 원은 현재 고장 장비, 주황 원은 아직 끝나지 않은 재배정 작업과 현재 차량 대기 연결에 따른 영향 대상이다. STS 재배정은 화물이 AGV로 인계되면, 야드 재배정은 화물이 야드에 적재되면 완료로 판정한다. 한 장비에 남은 재배정 작업이 없으면 주황 원이 사라지며, 과거 고장·수리 기록이나 다른 화물의 일반 배정만으로 계속 표시하지 않는다. 파란 점선은 AGV의 실제 남은 FMS 경로다. 주황 점선은 진행 중인 STS 담당 또는 야드 목적지 변경을 나타내는 **계획 연결선**이며 물리적인 주행 경로가 아니다. 완료된 계획 연결선도 사라지지만 아래 재배정 기록과 누적 재배정 횟수는 유지한다. 정지한 엔진의 기록에는 움직임을 만들어 표시하지 않는다.

지도 아래에는 엔진이 기록한 최근 128개 고장·수리·STS 재배정·야드 재배정 이벤트를 묶어 표시한다. 오류 발생 후 해당 장비의 새 이벤트를 추적하며 **전체 기록**으로 현재 실행의 나머지 이력을 볼 수 있다. 초기화 시 이벤트·제어 세션이 새로 시작된다.

## 통신

`POST /api/equipment-command`는 현재 실행의 `run_id`, `control_session`, 액터 ID, 허용된 고장/복구 동작만 받는다. STS/RMG는 `fail`, `fail_reboot`, `fail_sensor_repair`, `fail_gantry`, `repair`를, AGV는 `fail`, `repair`를 받는다. 웹 서버는 같은 출처 요청과 최근 엔진 상태를 확인하고 `Saved/Dashboard/commands`에 JSON을 원자적으로 발행한다. 엔진은 게임 스레드에서 명령을 읽고 실행 세션·10초 유효기간·대상·안전 오류를 다시 검사한다. 임의 콘솔 명령은 실행하지 않는다. 대기/PortSim 자체 일시정지 중에도 입력은 처리하되 물리 이동은 진행하지 않는다.

HTTP 202는 접수이며, `state.command_results`의 `applied`가 실제 적용 확인이다. 명령을 자동으로 재전송하지 않는다. 실행 재시작·리셋 뒤 이전 명령은 거절한다. 충돌·과부하 등 전체 안전 정지는 이 웹 수리 버튼으로 해제할 수 없다. 센서 고장 팝업은 오버뷰를 가리지 않으며 전체 안전 정지는 기존 대화상자로 표시한다.

## 검증 명령

구현 후 한 검증 단계에서 빌드, 웹 테스트, 네이티브 회귀 검증을 수행한다. 실제 연결 시험은 웹 서버 실행 후 `node Dashboard/tests/live-controls.mjs`를 먼저 실행하고 별도 프로세스에서 아래 통합 시험을 시작한다. 연결 시험은 웹 API로 두 크레인의 고장/수리와 적재 중 AGV의 고장/수리를 실행하며, 엔진 응답·화물 유지·다른 차량 이동·재배정 이벤트를 확인한다.

```powershell
./PortSim/Scripts/TestSite.ps1 -Mode Normal -PlaybackRate 0 -FixedFPS 5 -TimeoutMinutes 60 -NoSea -CheckStowage -ResultSummaryPath ./PortSim/Saved/Tests/WebControlSite.json
```

건조·선박 운동 OFF에서 600개 중 120개(20%)의 운송·복귀를 검사한다. 고장 입력 자체는 CLI 예약 입력 대신 웹 API로 실행한다. 결과는 `Saved/Tests/WebControlIntegration.json`, `Saved/Tests/WebControlSite.json`에 남긴다.

2026-10-20 실제 연결 시험 PASS: STS 2번·RMG 12번 고장/수리, 적재 중 AGV 102번 고장/수리의 엔진 응답을 확인했다. AGV의 위치·화물 유지 중 다른 AGV가 이동했고, 야드 목적지 25건의 재배정 이벤트가 기록됐다. 브라우저 버튼으로 RMG 1번 고장/수리도 확인했다. 총 4개 고장 이벤트를 포함한 120개 운송·복귀가 통과했다(마지막 적재 9,450.900141초, 복귀 9,644.7초). 정상 운용 대비 성능 비교치는 아니다. 상부 적재 58건·20ft 두 자리 적재층 13개를 확인했으며 두 화물 동시 운송은 이번 실행에서 성립하지 않았다.

표시 데이터도 보완했다. AGV 하중은 고정 0 대신 실제 `PayloadKg`를 내보내고, 격리 장비 수에 주행 고장 AGV를 포함한다. 비동기 JSON 기록 작업에 넘기는 명령 응답·이벤트는 중첩 좌표까지 별도로 복사하여 게임 스레드의 이력 변경과 공유하지 않는다.

최종 빌드 성공. 웹 자동검증 18개와 네이티브 34개 항목을 확인했다(기존 33개 회귀 검증 후 새 `DashboardSnapshotOwnership` 한 항목만 추가 확인). 브라우저 확인 화면은 `PortSim/Saved/Tests/WebEquipmentControl.png`, 네이티브 로그는 `WebControl_Units.log`와 `WebControl_SnapshotOwnership.log`에 남겼다.
