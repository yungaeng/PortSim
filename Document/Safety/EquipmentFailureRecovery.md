# 센서 고장 격리와 작업 재배정

## 고장 종류·자동 수리·대피 (2026-10-21)

- 웹의 장비 **오류·복구**에서 자동화 카메라 재부팅, 필수 센서 현장 수리, 갠트리 주행 고장을 선택한다. AGV의 기존 주행 고장 제어는 유지한다. 갠트리 고장도 장비 단위로 격리하며 센서 재부팅으로 해제하지 않는다.
- 기본 가정은 재부팅 60초, 현장 수리 900초, 센서 재확인 2초다. **OEM 실측 수리 시간이 아닌 편집 가능한 시뮬레이션 가정**이다. 에디터 `Failures → Repair`의 `Sensor Reboot Seconds`, `Sensor Technician Repair Seconds`, `Sensor Self Check Seconds`, `Auto Sensor Recovery`로 변경한다. 경과 시간은 시뮬레이션 시간이며 전체 일시정지/비상정지/장비 비활성화 동안 멈춘다. 갠트리 고장은 수동 수리를 기다린다.
- 시간이 지나도 안전 오류를 지우지 않는다. 센서 고장만 해제하고 기존 센서·잠금·착좌·하중·정렬 검사를 다시 거쳐 같은 작업을 이어간다. 강수/안개 때문에 관측이 계속 불가능하면 기존 센서 인터록이 다시 정지시킨다.
- 자동화 카메라 고장은 주행 엔코더·비상정지·충돌 방지계와 독립이라는 명시적 모델이다. `Allow Sensor Fault Evacuation`, `Independent Travel Safety Healthy`, 빈 스프레더, 안전 높이, 취소 가능한 미인양 작업 조건을 모두 만족해야 대피한다. 필수 주행 안전 센서 고장, 주행 모터 고장, 잠금/화물 유지, 낮은 스프레더에서는 대피하지 않는다.
- 대피 목표는 이웃 크레인의 실제/예약 작업 범위 사이에서 남은 화물을 덜 막는 위치다. A–B–C 순서를 유지하며 **B가 C를 지나 C 바깥으로 대피하는 동작은 허용하지 않는다.** 25m 중심 간 여유는 기존 블록아웃 가정이다. 서비스 주행은 최대 0.25m/s, 가속도 최대 0.1m/s²와 레일 마찰 한계를 사용한다. 정지 거리·보기 상부 충돌 검사와 현수 동역학을 적용한다.
- 수리가 완료되면 서비스 주행을 감속 정지한 뒤 원래 레일 기준점으로 복귀한다. 다른 크레인의 예약이 있으면 기다린다. 실제 복귀 전에는 새 작업을 배정하지 않는다. 고장 중 유지한 화물은 대피/복귀로 옮기지 않는다.
- 기존 CLI `FailureAt/RepairAfter` 시나리오는 명시적 수리 시각을 유지한다. `-PortSimAutomaticSensorRepair` 또는 `TestSite.ps1 -AutomaticSensorRepair -RepairAfter -1`로 개별 센서 자동 복구 시간을 사용할 수 있다.

참고: [Li et al., Real-Time Disruption Recovery 초록](https://journals.sagepub.com/doi/10.3141/2479-07)은 복구 시 기존 계획을 조정하는 모형을 설명한다. 위 수리 시간이나 독립 안전계 가정의 출처는 아니다.

## 실행 중 고장/수리

플레이 중 아웃라이너의 `Working_STS_..` 또는 `Working_RMG_..`를 선택해 **Failures → Sensor Fault**를 체크한다. 체크 해제 또는 **Repair Sensors**로 수리를 알린다. Blueprint에서는 `SetSensorFailure(bool)`와 `RepairSensors()`를 사용한다. 수리는 고장 표시를 제거하고 기존 센서 제어를 재개하게 하며, 화물·잠금·계획을 강제로 초기화하지 않는다. 실제 관측/잠금/정렬 조건이 여전히 나쁘면 원래 인터록이 작동한다.

선택 장비의 시간 지정 입력:

```
-PortSimFailedSTS=2 -PortSimFailedRMG=12 -PortSimFailureAt=60 -PortSimRepairAfter=900
```

STS 번호는 1~9, RMG 번호는 1~46이다. 고장 시각과 수리까지의 기간은 시뮬레이션 초이며 배속을 따른다. 수리 기간을 생략하거나 -1로 주면 자동 수리하지 않는다. 전체 일시정지/비상정지 동안 이 시계도 멈춘다. 기존 `PortSimSTSSensorFault`/`PortSimRMGSensorFault`는 모든 장비의 필수 센서를 차단하는 **기존 전체 정지 회귀 시험용 입력**으로 유지한다. 개별 고장에는 새 번호 입력이나 장비 API를 사용한다.

## STS

- 미인양 작업은 같은 선박의 원래 담당 STS와 바로 이웃 STS에서 정상·유휴·도달 가능한 장비를 찾는다. 기존 AGV, 화물 ID, 인수 위치와 야드 예약은 유지한다.
- 갠트리는 기존 가감속·센서·스웨이 제어로 이동한다. 고장 크레인과 다른 크레인의 현재/예약 작업 구간을 통과하지 않는다. 블록아웃 크레인 중심 간 25m를 보수적인 이동 여유로 가정하며 OEM 제한 수치가 아니다. 복구 중 레일 인터록이 걸리면 관련 작업만 기다린다.
- 이미 잠금이 걸렸거나 매달린 화물은 취소·탈착·다른 크레인에 순간 인계하지 않는다. 해당 크레인과 AGV 작업을 유지하고 수리 대기한다. 해제 후 안착 검증만 남은 작업도 수리가 필요하다.
- 대체 STS가 닿지 못하는 고장 크레인 바로 아래 구간은 기다린다. 옆 STS가 모든 구간을 무조건 처리한다는 가정은 하지 않는다. 수리 후 아직 시작하지 않은 작업은 원래 담당 구역으로 복귀한다.
- 미착수 화물의 대체 가능성은 **대체 STS 자신의 인수 위치**로 계산한다. 이미 배정된 AGV의 작업은 기존 인수 위치를 보존한다. 고장 STS가 매단 화물과 그 바로 아래 구간은 이 수정으로 강제 인계하지 않는다.
- 고장으로 STS 인수가 중단되면, AGV가 야드에서 40m 이상 떨어져 있고 아직 RMG 작업을 시작하지 않은 경우 미사용 야드 접근권을 반환한다. 컨테이너 슬롯 예약은 유지한다. 복구된 작업은 접근권을 다시 확보한 뒤 하강·인계를 재개하며 다른 AGV의 예약을 빼앗지 않는다.
- 고장 STS 때문에 도착할 수 없는 아래층 화물에 의존하는 **미착수 야드 계획**은 모든 상부 의존 예약을 포함해 별도 지원 가능한 슬롯으로 함께 재배정한다. 화물의 선박 위치와 STS 담당은 이 야드 재계획으로 바꾸지 않는다. 이미 운송 중/적재 완료 화물의 목적지는 고정하고, 크기·20ft 두 자리 지지·취급/위험물·출고 구역·중량 조건을 유지한다. 고장 STS의 작업이 모든 야드의 지지 조건을 막는 연쇄 대기를 방지한다.

## RMG

- 이미 야드에 적재한 화물, 고장 장비가 유지 중인 화물, 해제 후 검증 중인 화물은 고정한다. 그 외 해당 RMG 목적지와 그 아래층/20ft 두 자리 의존 계획을 함께 다시 배치한다.
- 20/40/45ft 구역, 두 자리 지지, 출고 구역·순서, 취급 유형·위험물, heavy→light, 누적 상재하중과 정상 RMG 도달 범위를 유지한다. 사용 가능한 슬롯을 무작정 거리 순으로 선택하지 않는다.
- 한 고장 RMG의 영향을 받는 계획 전체가 가능할 때만 새 슬롯·작업·접근 예약을 함께 반영한다. 불가능하면 기존 계획과 예약을 보존하고 해당 작업을 대기시킨다. 다른 고장 RMG의 계획은 별도로 시도한다.
- 화물을 운반 중인 AGV는 승인된 기존 도로를 따라 기존 야드 진입/인수 지점에 정지한 뒤 목적지를 바꾼다. 기존 야드의 실제 출구를 새 경로 그래프에 포함한다. 아직 통과 중인 도로 예약을 빼앗거나 차체를 횡이동/텔레포트하지 않는다.
- 새 RMG의 접근권을 확보한 뒤, 이전 RMG의 접근권은 AGV가 이전 인수점과 진출 통로를 실제로 벗어났을 때 반환한다. 한 AGV에 실린 20ft 두 화물은 같은 RMG로 보내 기존 두 번의 독립 검증 인계를 유지한다.

## 관측·초기화

웹 개요는 장비 고장과 전체 정지, 화물 유지, 레일 간격 대기, 컨테이너 담당 변경과 재배정 불가 이유를 구분한다. 루트 데이터에는 장비 고장 이벤트·STS/야드 재배정 횟수, 컨테이너에는 원래/현재 STS·재배정 횟수·대기 이유를 기록한다. CSV 프로필에도 이벤트 수를 남긴다. 공통 작업 시계는 계속 진행하므로 고장 대기·우회로 인한 손실은 전체 완료시간에 포함된다.

리셋은 최초 화물·야드 계획을 복원하고 고장/예약/재배정 상태를 지운다. 지정한 시간 시나리오는 새 실행에서 다시 시작된다. 수리만으로 이미 확정된 야드 목적지를 다시 옮기지 않는다.

## 수동 STS 2번 고장으로 발생한 연쇄 대기 수정

2026-10-20 `PortSim.log`와 종료 직전 상태를 확인했다. 35,381.5 시뮬레이션 초에 454/600개가 적재됐고, STS 2번은 13.3t 화물을 유지한 채 센서 고장으로 정지했다. 남은 해당 STS 화물은 유지 중 1개와 선박 내 66개이며, STS 재배정은 0건이었다. 20ft 두 자리의 지지 조건까지 포함하면 다른 STS의 화물 49개가 해당 화물의 야드 아래층 예약에 직접/간접 의존했고, AGV 123은 STS 2번을 기다리면서 RMG 16 접근권을 계속 점유했다.

미착수 화물의 후보 STS 인수 위치 계산, 고장 픽업의 미사용 야드 접근권 반환/재확보, 모든 상부 예약을 포함하는 야드 의존 그룹 재계획을 보완했다. 접근권 반환은 슬롯 예약 취소가 아니며, 공용 도로의 실제 주행 예약·LiDAR·크레인 레일 간격·잠금과 하중 인터록을 유지한다. STS로 접근하는 차량은 공용 도로를 계속 이동할 수 있지만, 인수 이후 운송을 시작하기 전에 야드 접근권을 다시 확보해야 한다.

수정 전 상태는 `PortSim/Saved/Tests/STS2_ManualFault_Before.json`에 보존했다.

### 이번 수정의 실행 검증

- 최종 UE 5.6 빌드, 복구 네이티브 시험 2개(`EquipmentFailures`, `DashboardSnapshotOwnership`), 관련 웹 시험 6개가 통과했다. 최종 네이티브 로그는 `PortSim/Saved/Logs/STSRecoveryFix_Final.log`다.
- 600개 매니페스트에서 STS 2번을 60초에 화물을 유지한 상태로 고장 내고, 6,060초에 수리했다. 실제 운송 169개(28.2%)까지 안전 상태 검사를 유지했다. 고장 중 수리 전 완료가 127개(21.2%)이고 STS 4~9번 모두 운송을 완료했다.
