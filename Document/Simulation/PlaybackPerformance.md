# 배속 성능 회귀와 수정

## 확인한 원인

- `e5827bd`에서 통합 터미널의 초기 야드 재고를 비웠다. 다만 이후 `e789b25`(4·8배속 검증)에도 이미 같은 변경이 포함돼 있으므로, 야드를 비운 것만을 회귀 원인으로 단정할 근거는 없다.
- 이후 선박 운동 보간에서 선박 위 600개 컨테이너의 엔진 충돌체·외형을 매 0.05초마다 갱신하고 있었다. 화면 한 프레임에 여러 초를 처리하면 같은 외형을 수십 번 갱신했다.
- 컨트롤러의 60/120 Hz 계산에서 센서 설치 문자열·참조 JSON까지 포함된 설정 배열을 복사하고, 변하지 않는 텔레스코픽 형상도 반복 갱신했다.
- 엔진 통계에서 자유 물리 운동을 하는 물체가 없는 프레임에도 Chaos가 241회 실행됐다. 예시 로그 `PlaybackPerf_Engine.log`의 `TG_EndPhysics`는 한 프레임 약 317 ms다. 충돌 검출 자체보다 반복 적분·결과 버퍼링 비용이 컸다.

## 적용 방식

1. **질의 전에 필요한 충돌체를 동기화한다.** 선박 컨테이너 전체의 Hermite 운동 경로를 Bezier 제어점으로 감싸고, 회전 중 모서리 이동량을 더한 보수적인 범위를 만든다. STS/RMG 지지면·목적지·충돌 센서 질의와 겹칠 수 있는 컨테이너는 질의 직전에 해당 제어 시각의 정확한 보간 위치로 옮긴다. 선택된 집기 대상은 매 제어 단계에 갱신한다. 화면 프레임 끝에는 나머지 컨테이너도 모두 동기화하므로 다음 엔진 물리 단계와 외부 클릭 질의는 완성된 장면을 본다.
2. **외형 갱신을 모은다.** 충돌이 없는 컨테이너 외형과 와이어 외형은 화면 프레임 끝에 갱신한다. 크레인 부품은 센서 측정·결합·충돌 질의 전과 작업 단계 끝에 동기화한다. 웹 스냅샷도 장면 동기화가 끝난 프레임 경계에서 만든다.
3. **필요한 계산만 복사한다.** 수치 물리 파라미터와 센서 설치 목록을 분리했다. 빈 크레인은 제어 반복을 수행하지 않으며, 배차 후보는 해당 STS의 목록에서 찾는다. 센서·동역학 계산식과 인터록은 유지한다.
4. **시간 분할의 실수 오차를 보정한다.** float `0.05`를 60 Hz로 환산한 `3.0000000447`을 4회로 올림하지 않는다. 의도된 60 Hz 제어·120 Hz 구동 적분을 사용하고, 실제 초과 시간은 여전히 추가 단계로 나눈다.
5. **완전히 운동학적인 프레임의 빈 적분을 생략한다.** 통합 터미널에서 월드 전체의 물리 컴포넌트를 확인한다. 자유 강체(잠든 강체 포함), 지원하지 않는 물리 객체, 비동기 물리 또는 네트워크 예측이 있으면 기존 물리를 사용한다. 모두 고정/운동학적 객체인 경우에만 Chaos의 시간 0 프레임으로 충돌 질의·프록시 동기화를 유지한다. 이때 이동한 충돌체의 실제 강체 위치도 명시적으로 동기화한다. 그렇지 않으면 시간 0 동안 쌓인 운동학적 목표가 다음 자유 강체 프레임에 과거 위치에서 재생되어 착지 오류를 일으킨다. 컨테이너 해제 후 자유 강체가 생긴 프레임은 원래 시간·서브스텝 설정을 복원한다. 앱 시간과 교통·센서·진자 시간은 줄이지 않는다.
6. 사용하지 않는 겹침 이벤트 콜백과 정적인 표지판의 매 프레임 Slate 재그리기를 없앴다. 물리 충돌과 명시적인 레이/겹침 질의는 유지한다.

## 재현

```powershell
# 실제 처리한 시뮬레이션 시간 / 벽시계 시간. 기본값은 CPU 비교용 null RHI.
./PortSim/Scripts/MeasurePlayback.ps1 -PlaybackRate 8 -Seconds 60

# 1280×720 렌더링 포함. 에디터의 4K 뷰포트 성능과 같다는 뜻은 아니다.
./PortSim/Scripts/MeasurePlayback.ps1 -PlaybackRate 8 -Seconds 60 -Render

# 같은 코드에서 빈 Chaos 적분 생략만 끄고 비교.
./PortSim/Scripts/MeasurePlayback.ps1 -PlaybackRate 8 -Seconds 60 -FullPhysics

# 구간별 CPU 시간과 엔진 프레임 통계.
./PortSim/Scripts/MeasurePlayback.ps1 -EngineStats

# 기본 검사와 120/600개(20%) 실제 하역·복귀, 웹 데이터 검사.
./PortSim/Scripts/TestShipArrival.ps1 -PlaybackRate 8 -Profile
```

`-PortSimFullPhysics`는 빈 물리 적분 생략만 해제하는 진단 옵션이다. 일반 실행에서는 최적화를 자동 적용한다. 프로파일은 `-PortSimProfile`을 명시한 실행에서만 수집한다.

## 검증 범위

추가한 기본 검사는 겹침 이벤트를 끈 상태의 실제 레이·겹침 질의, 같은 프레임의 이동 반영, 외형 지연 후 복원, Hermite 오버슈트·회전·부분 시간창의 60개 질의와 전체 갱신 기준의 충돌점 일치, float 시간 분할, 자유/수면 강체의 정상 물리 복귀를 검사한다. 실제 배속은 설정값을 그대로 표시한 값이 아니라 완료한 교통 단계의 시뮬레이션 시간으로 측정한다.

수정 전 같은 600개 초기 배치·환경 시드에서 8배속 선택 후 60.293초 동안 150.600초를 처리했다(실제 **2.498배속**). 원본: `PortSim/Saved/Logs/PlaybackPerf_Before.log`.

수정 후 CPU 진단 실행에서는 60.035초 동안 466.500초를 처리했다(실제 **7.770배속**, 기존 측정의 약 **3.11배**). STS→AGV 및 AGV→RMG 인계를 통과했으며, 오류 없이 종료했다. 원본: `PortSim/Saved/Logs/PlaybackPerf_Transition.log`, 요약: `PortSim/Saved/Tests/PlaybackPerf_Transition.json`.

장시간 검증은 `TestShipArrival.ps1 -PlaybackRate 8 -Profile`로 수행했다. 기본 검사 **27개**, 프런트엔드 검사 **9개**와 문법 검사, 도착 배치 웹 데이터 검사가 통과했다. **600개 중 120개(20%)를 실제 STS→AGV→RMG→야드로 운반하고 AGV 복귀까지 완료**했다. STS 9대 전체, AGV 54대가 작업했고 최대 19대가 동시에 이동했다. 크기 분리, 20ft 두 칸 적재층 13개, 지지되는 상부 적재 58개를 확인했다. 20ft 2개를 한 번에 운반한 작업은 이번 실행에서 발생하지 않았다.

- 마지막 적재: 시뮬레이션 `11,998.850179초`; 복귀 완료: `12,211.8초`.
- 마지막 프로파일 표본: 실제 `1,704.650초` 동안 시뮬레이션 `12,176.050초` 처리, 누적 **7.143배속**. 8배속을 모든 부하 구간에서 유지했다는 뜻은 아니다. 자유 강체가 겹치는 초기 운용 구간에서는 누적 약 6.2~6.7배속까지 내려갔다.
- 기본 검사: `PortSim/Saved/Logs/ShipArrival_Units_20261017_050725.log`.
- 실제 하역: `PortSim/Saved/Logs/SiteTest_Normal_Depot_Reused_29808.log`.
- 요약/웹 스냅샷: `PortSim/Saved/Tests/ShipArrival_20261017_050725.json`, `ShipArrival_20261017_050725_state.json`.
- 운반 기록: `PortSim/Saved/Results/Site_15CB304E476028A9C687FA872BD496F4.csv`.

위 수치는 null RHI로 CPU 처리량을 측정한 결과다. 렌더링과 에디터의 고해상도 뷰포트 비용은 별도로 구분한다.

렌더링을 켠 별도 실행은 RTX 3050 Laptop GPU, D3D12, 1280×720 창에서 60.155초 동안 시뮬레이션 424.550초를 처리했다(**7.058배속**). 첫 실행의 PSO 생성 지연을 포함하며 오류 없이 종료했다. 원본: `PortSim/Saved/Logs/PlaybackPerf_Render.log`, 요약: `PortSim/Saved/Tests/PlaybackPerf_Render.json`. 이 측정은 60초 구간이므로 120개 전체 렌더링 검증이나 4K 에디터 성능을 뜻하지 않는다.
