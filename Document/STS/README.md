# STS 도면·센서 자료 분석 및 프로젝트 적용 명세

분석일: 2026-09-23. 코드 기준: `junsoo`, `13e007e`.

후속 개발 범위와 우선순위는 [STS 코드 확장 계획](ImplementationPlan.md)에 정리했다.
현재 코드에 연결된 항목과 실행 방법은 [런타임 적용 내역](RuntimeApplication.md)을 참고한다. 아래 코드 관찰은 초기 조사 시점의 상태다.

**목표:** PortSim은 선박에서 야드까지의 컨테이너 운반을 자동화하여 전체 작업의 시간 이득을 계산한다. 현재 STS 범위는 아래 변수·사양·센서를 동작과 제어 판단에 적용해 선박의 컨테이너를 AGV에 자동 인계하고 다음 작업을 수행하는 것이다. 변수 비교는 보조 검증이며, 주 결과는 조건을 반영해 완료한 자동 운반과 작업·대기 시간이다.

## 1. 자료의 범위와 사용 원칙

- [GA 원본 PDF](References/ga-zpmc-qc8-12.pdf): 1페이지 스캔 도면. 회전한 전체 페이지와 사양표·표제란 확대 이미지를 육안 확인했다. 도면 번호 **J5300**, 제조사 **ZPMC**, 표제 **OMAN 65LT CONTAINER CRANE / GENERAL ARRANGEMENT**, 구조물 표기 **PORT OF SALALAH**를 판독했다. 파일명의 QC8-12와 개별 장비 일련번호의 대응은 미확인이다. 개정·승인·날짜는 확정하지 않았다.
- [센서 원본 TXT](References/STS_Crane_Sensor_Layout_AI_Reference.txt): STS 센서 **14종**의 대표적 설치 위치·용도·입출력 참고자료. 이 도면의 실제 출고 사양이나 설치 목록이 아니다.
- [구조화 참고 데이터](STS_ReferenceData.json): 판독값, 단위 변환값, 센서 후보, 미확정 변수, 코드 연결 지점을 저장한다. 런타임 로더가 필요한 값을 추출하고 별도 가정 설정과 결합한다. 원본 자체가 완성된 운전 설정이나 실제 장비 승인 사양은 아니다.
- 원본 두 파일은 내용 변경 없이 복사했다. SHA-256은 JSON에 기록했다.
- TXT의 `AI_USAGE_HINT`, 구현 우선순위, 제어 예시는 자료의 내용으로만 취급했다. 프로젝트 수정 지시로 실행하지 않았다. 초기 분석은 문서·참고 데이터 추가에 한정했고, 이후 사용자 요청에 따라 [런타임 적용](RuntimeApplication.md)을 진행했다.
- 루트 README의 부산항 신항 DGT 계획 수치와 이 오만/살랄라 장비 도면은 **서로 다른 출처**다. 하나의 실장비 프로파일로 섞지 않는다.

데이터 상태는 `drawing_read`(도면 판독), `derived`(명시한 계산), `reference_typical`(대표 센서 사례), `proposed`(프로젝트 설계안), `unknown`(미확정), `current_code`(현재 코드 관찰)로 구분한다. `drawing_read`도 현장 실측이나 제조사 재승인을 뜻하지 않는다. `null`은 0이나 미설치가 아니라 미확정이다.

### 2.4 도면이 보여주는 구조와 보여주지 않는 것

기계실 평면, 정면(View A), 측면, View B/C-C, **Main hoist / Trolley / Boom hoist / Catenary trolley rope reeving**의 네 개 줄걸이 개략도가 있다. 기계실·메인 트롤리·보조 트롤리·붐 권상계를 분리하는 근거로 사용할 수 있다.

그러나 이 스캔만으로 각 로프의 정확한 지지 가닥 수, 로프 경로 순서, 모든 앵커 좌표, 시브 지름, 각 드럼과 모터의 기계적 연결을 확정하지 않았다. 도면의 `rope tension device`를 하중 센서라고 단정하지 않는다. 품목 번호는 센서 번호가 아니다. 센서 TXT의 A-M 표시도 원 도면의 품목 번호나 View A/B와 대응하지 않는다.

- TXT ASCII 그림의 권상 엔코더가 와이어 위에 그려져 있어도 이를 실제 장착 위치로 쓰지 않는다. 본문의 축/드럼/구동계 후보를 따르고 상세도에서 확정한다.
- 단일 40ft부터 시작하는 설계에서는 TTDS·신축 기능을 후순위로 둘 수 있다. twin-lift를 구현할 때는 지지점·잠금 개수·컨테이너별 하중 채널을 다시 정의해야 한다.
- **Landed는 1단계로 승격했다.** TXT의 우선순위를 그대로 따르지 않고 잠금 명령의 선행 조건으로 배치했다.
- 스프레더 착좌와 컨테이너가 AGV/선박/야드에 지지되는 것은 서로 다른 접촉이다. 전자만으로 화물 해제 허가를 내리지 않는다.
- 풍속계 측정값 자체가 외력을 만드는 것은 아니다. 환경 바람이 물체에 힘을 가하고, 센서가 바람을 관측하며, 제어기가 관측값에 따라 운전을 제한하도록 분리한다.
- 실제 영상 인식이 없다면 정렬 점수는 `synthetic_pose` 등 합성 관측임을 표시한다. 카메라 영상만 표시하면서 실제 CV 측정이라고 주장하지 않는다.

## 4. 하중·센서·제어 모델을 분리하는 방법

다음은 제공 자료를 적용하기 위한 **프로젝트 설계안**이다.

### 4.1 단위와 좌표

- 저장·계산 기준: m, s, kg, N, N·m, rad. 도면의 kW/rpm/deg는 원문을 함께 보존한다.
- UE 위치 경계에서 m -> cm는 x100, 도면 mm -> cm는 /10, m/min -> cm/s는 x100/60이다.
- 힘·토크를 엔진에 전달할 때도 해당 API의 단위를 확인해 변환한다. cm 기반 역학량을 요구하는 경계라면 N -> kg·cm/s²는 x100, N·m -> kg·cm²/s²는 x10,000이다. 표시 단위와 물리 API 단위를 혼용하지 않는다.
- 크레인 로컬 원점 제안: 해측 레일 상단의 STS 중심선 교점. +X 육측, -X 해측, +Y 안벽/갠트리 주행 방향, +Z 위. 현재 코드의 바다(-X)/육지(+X) 방향과 맞추되 원점은 별도 변환한다.
- 현재 컨테이너의 긴 축은 Y다. FL/FR/RL/RR 명칭에는 스프레더 로컬 전방·좌우 정의를 반드시 붙이고, 실제 소켓 좌표로 하중 채널을 매핑한다. 미확정인 지금은 모서리 좌표를 `null`로 둔다.
- 그림의 페이지 좌표/픽셀 크기를 곧바로 실좌표로 변환하지 않는다. 기계실의 1:125 표기를 전체 페이지 공통 축척으로 쓰지 않는다.

### 4.2 하중 구분

1. **컨테이너 하중**: 스프레더 아래 하중. 트위스트록 로드셀의 모델링 대상이다.
2. **서스펜션 하중**: 컨테이너 + 스프레더 + 헤드블록 등 지지되는 모든 질량과 동적 효과. 위의 4개 센서 합과 같지 않다.
3. **개별 와이어 장력**: 실제 줄걸이, 기울기, 로프 강성·감쇠, 하중 분배로 계산한다. 트위스트록 수와 로프 지지 가닥 수는 별개다.
4. **모터/드럼 하중**: 로프 장력·드럼 반경·감속비·효율·회전 관성·브레이크를 통해 연결한다. 모터 전류로 표시하려면 별도 전기 모델/토크 상수가 필요하다.

수평·준정적·완전 현수 조건에서 코너의 수직 반력 `F_i`로 `sum(F_i) ≈ m_container * g`, `x_cog ≈ sum(F_i*x_i)/sum(F_i)`, `y_cog ≈ sum(F_i*y_i)/sum(F_i)`를 검사할 수 있다. 가속·회전·접촉 중에는 그대로 질량/무게중심으로 환산하지 않는다. 정적 힘·모멘트 평형만으로 네 코너의 실제 분담이 항상 유일하게 정해지는 것도 아니다. 강성/접촉 모델 또는 명시적인 분배 가정이 필요하다. 모든 모서리를 무조건 `mg/4`로 만드는 모델은 편하중 검증에 사용할 수 없다.

### 4.3 공통 센서 인터페이스

센서 정의: `id`, `parent_frame`, `local_position_m`, `local_rotation_deg`, `measurement_kind`, `unit`, `sample_rate_hz`, `latency_s`, `noise_stddev`, `bias`, `range`, `fault_mode`.

관측 메시지: `sensor_id`, `simulation_timestamp_s`, `sequence`, `measured_value`, `valid`, `fault_code`. 물리 참값은 진단/정답 스트림에 별도 기록한다. 제어기가 센서 고장을 우회해 참값을 몰래 읽지 않도록 한다. 미수신·지연 초과·범위 초과는 정상값 0으로 대체하지 않는다. 허용 지연/고장 시 정책은 아직 미확정이다.

### 4.4 anti-sway와 anti-skew

| 항목 | 필요한 관측 | 필요한 구동 권한 | 이번 자료의 확인 상태 |
|---|---|---|---|
| Anti-sway | 횡/종 흔들림 각도·각속도, 로프 길이, 트롤리 상태 | 트롤리/권상 명령에 대한 설계된 보정 | 실제 탑재 여부·알고리즘·게인 미확정 |
| Anti-skew | 스프레더의 목표 대비 yaw 오차·각속도 | 차동 로프 제어 또는 별도 skew 구동 등 실제 기구 | 3° 표기만 확인. 센서·구동 기구·제어 여부 미확정 |

TXT에는 직접적인 sway/skew 자세 센서가 별도 항목으로 없다. 자세 카메라·IMU·로프각 센서·상태 추정기 중 어떤 방식을 사용할지 추가 정의해야 한다. `installed_on_reference_crane`와 `simulation_enabled`를 구분한다. 모델과 액추에이터가 준비된 뒤 같은 시나리오에서 ON/OFF를 비교한다. 회전을 강제로 0으로 고정한 상태를 anti-skew 제어 성공으로 계산하지 않는다.

## 5. 현재 프로젝트와의 차이 및 연결 위치

아래 경로는 저장소 루트 기준이다. 기능을 조사했으며 이번 작업에서 수정하지 않았다.

| `PortSim/Source/PortSim/TerminalLayout.h` | 야드/레일/슬롯 좌표 상수 | 실제 STS 크기에 맞춰 선박·AGV·야드 배치를 함께 재검토 |

현재 STS의 갠트리 속도는 공통 `TravelSpeed * 0.6`으로 계산된다. 터미널 모드에서는 210cm/s가 되어 도면의 100cm/s와 다르다. 트롤리 400cm/s만 반영해도 갠트리 속도가 함께 바뀌므로 독립 속도 제한이 필요하다. 현재 권상 250cm/s 역시 도면의 65 LT 조건 88.33cm/s와 다르다. 이는 도면과 현재 프로토타입이 다르다는 의미이며, 현재 12t 화물에 65 LT 속도를 곧바로 적용하라는 뜻은 아니다.

또한 현재 권상 로프 범위 4-28m와 인양 범위 55.2m는 서로 다른 물리량이다. `MaxRope=5520`처럼 치환하면 안 된다. 트롤리 지지 높이, 스프레더 기준점, 줄걸이와 작업 하한을 함께 정의해야 한다.

## 6. 구현 순서와 검증 시나리오

### 단계 1: 단일 40ft 인양·인계와 관측 기반 제어

장비 프로파일/단위/좌표 정의 -> 컨테이너·스프레더 질량 분리 -> 서스펜션과 접촉 모델 -> 엔코더·하중·잠금·착좌·AGV 위치 관측 -> 상태 제어기 -> HUD/로그.

제안 순서: 목표 접근 -> 저속 착좌 -> 필요한 코너의 착좌 확인 -> 잠금 명령 -> 잠금 확인 -> 저속 시험 인양과 하중 안정화/과부하 확인 -> 작업 높이 인양 -> 수평 운반 -> AGV 정차/정렬 확인 -> 저속 하강 -> **화물이 AGV에 지지되고 잠금부 하중이 충분히 해제된 상태** 확인 -> 잠금 해제 -> 스프레더 이탈 -> 완료.

스프레더가 아직 빈 상태로 상승할 때는 `all locks locked`를 요구하지 않는다. 빈/적재 상태, 센서 유효성, 리미트·브레이크 상태를 포함하는 상태별 허가가 필요하다. 미확인 센서나 임계값은 허가로 자동 변환하지 않는다.

### 단계 2: 외란·충돌 관측을 반영한 안정적인 자동 운반

바람 물리 모델과 풍속계, 붐/갠트리 장애물 검출, 선박 프로파일, 카메라·자세 관측을 자동 운반 판단에 연결한다. Anti-sway는 관측/구동 인터페이스를 통해 이동과 착지에 적용한다. Anti-skew는 yaw 자유도와 구동 기구가 확보된 뒤 적용한다. 제어 효과 비교는 정상적인 반복 자동 인계가 이루어지는지 확인하는 보조 검증이다. 센서 고장 시 브레이크·감속 정책도 장비 상태별로 정의한다.

### 단계 3: 전체 항만 자동화와 시간 이득 계산, 선택 기능 확대

STS 인계 이벤트를 AGV 운반·RMG 적재에 연결하고 전체 작업 시작부터 마지막 야드 적재까지의 시뮬레이션 시간을 기록한다. 장비 병렬 운전과 대기를 반영해 기준 운용 대비 시간 이득을 산정한다. 기준 운용 방식은 별도 정의가 필요하다. 신축·TTDS/twin-lift는 실제 취급 범위가 요구할 때 상세도와 함께 확대한다. 이 두 첨부자료에는 AGV·RMG의 모터/물리 사양이 없다.

### 검증 항목

| 시나리오 | 확인할 결과 |
|---|---|
| 단위·기하 | m/min -> cm/s, 레일 간격·도달거리·인양 기준점 일치 |
| 중심/편심 하중 | 준정적 힘·모멘트 평형, 코너별 분담 변화, 각 와이어 장력 |
| 부하별 권상 | 빈 스프레더와 유부하 곡선 구분, 한계·브레이크·가감속 반영 |
| 하나의 잠금 실패/착좌 오검출 | 해당 상태에서 인양 또는 잠금 전환 거부 |
| 센서 지연·고장·편향 | 유효성 확인, 상태별 정책, 참값 우회 없는지 확인 |
| AGV 오정렬/이동 | 착지 허가 보류, 지지 확인 전 해제 금지 |
| Anti-sway/anti-skew ON/OFF | 같은 질량·바람·경로에서 최대각/RMS/잔류각/안정화시간/작업시간 비교 |
| 1x/2x/4x/8x/16x 재생 | 물리 스텝·센서 시계·제어 주기 일관성, 재생 배속에 따른 결과 오차 기록 |

허용 오차, 안정화 시간, 과부하/풍속/충돌 임계값은 제공 자료에 없으므로 아직 숫자를 부여하지 않는다. 빌드·실행·동역학 검증은 이번 문서화 작업에서 수행하지 않았다.
